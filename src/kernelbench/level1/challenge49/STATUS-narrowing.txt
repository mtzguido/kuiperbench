Why these did not land in this session
--------------------------------------

The prior session's STATUS-narrowing.txt explicitly estimated the
Block.fst clone at "6–10 hours of careful Pulse proof work" with
the hard rule "no admits on main; if you cannot finish, branch and
STATUS.txt".  That rule applied directly to this session: the
706-line Pulse module Kuiper.Kernel.HReduce.Block.fst is the
limiting clone, and its proofs are tightly coupled to the
sum-monoid.  Replacing rsum / + / 0 / %~ with seq_fmax / fmax /
neg_inf / == is mechanical *in spirit*, but each replaced
[assert pure (acc %~ rsum (seq_take ...))] becomes
[assert pure (acc == seq_fmax (seq_take ...))] and must
re-typecheck under Pulse — which routinely needs SMT debugging
passes the rule budget does not cover in a single agent session.

Therefore this session focused on landing every spec-side artefact
that *can* be ADMIT=0 within budget — Math.Fmin, Spec.MinReduceDim,
Spec.ArgmaxReduceDim, Spec.ArgminReduceDim — leaving the kernel
proofs as the still-unblocked work.

The math infrastructure (Phase A for each carrier) and the four
specs above remove all remaining design ambiguity — the next agent
picking up the clone can treat the spec / monoid axioms as fixed
contracts and concentrate purely on the Pulse proof obligations.

Unblock path — #53 min-reduce  (preferred: composite)
------------------------------------------------------

Path (b): [min(x) = -max(-x)].  Implementation:

  1. Launch a Map kernel: [y = -x]  (existing infra suffices —
     check Klas.Map or equivalent; if absent, a thin pointwise
     negate kernel is far cheaper than cloning Block).
  2. Launch the Max-reduce kernel from #49 on the negated tensor.
  3. Launch a Map kernel on the row reductions: [out = -tmp].

Two of these three launches are pointwise Maps (very cheap).
The middle one is exactly #49.  Total *new* Pulse code: only the
KB-layer composer + Python harness + bridge.  Spec bridge:
  seq_fmin s = -.  seq_fmax (seq_map negate s)  — provable from
  IEEE-754 negation being involutive and order-reversing on
  non-NaN; expose as a one-line lemma in Kuiper.Math.Fmin.

PyTorch tolerance: bit-exact on non-NaN inputs.

Path (a) (direct clone of Block.Min with (fmin, pos_inf)) is
~700 LOC — strictly avoid unless path (b) hits a snag.


Unblock path — #51 argmax / #52 argmin
---------------------------------------

These reduce over (value, index) pairs.  The current Block
infrastructure is scalar-typed and cannot host the pair monoid
without significant changes.  Two routes:

  Route 1 — pair-monoid generalisation
       Generalise HReduce.Block to an arbitrary [scalar] with a
       user-supplied associative binary op.  This is similar in
       effort to the original sum→max clone but more invasive
       because of the dependent index type.  Triaged as expensive.

  Route 2 — two-pass
       Launch 1: max-reduce → values per row.   (= #49 verbatim)
       Launch 2: per-row scan to find first index where
                 [x[i] == max_value].

  Launch 2 needs a small bespoke kernel: per-row, all threads scan
  the row, each writes its index if it hits the max value, and the
  thread with the smallest index wins (CAS or block-min on a
  shared cell).  Total new Pulse: ~400 LOC + spec bridge.

Recommend Route 2.  Spec bridge:
  is_seq_argmax s k  iff
       (s @! k == seq_fmax s) ∧ (∀ i<k. s @! i ≠ seq_fmax s)
  is preserved by the two-pass strategy because Launch 1 fixes
  [seq_fmax s] and Launch 2's first-index property is exactly the
  predicate.

NaN handling for argmax/argmin matches torch's semantics modulo
the same IEEE-754 caveats as the [fmax]/[fmin] axioms.


Skeptic findings (this session)
-------------------------------

Trusted-base additions in this session, all in
src/lib/kuiper/Kuiper.Math.Fmin.fsti:

  1. [val pos_inf : f32]
       Justification: opaque value extracting to (+INFINITY).
       Same idiom as Kuiper.Float32.zero / one and Math.Fmax.neg_inf.

  2. [val fmin_assoc : squash (is_associative fmin)]
  3. [val fmin_comm  : squash (is_commutative  fmin)]
       Justification: IEEE-754 fmin on non-NaN inputs is bit-exact
       associative and commutative.  Same NaN-quiet caveat as
       Math.Fmax.{assoc,comm} — project precedent.

  4. [val fmin_pos_inf_neutral : squash (is_neutral_for pos_inf fmin)]
       Justification: fmin(+inf, x) = x for non-NaN x.
