CURRENT AUDIT NOTE (2026-09-03)
--------------------------------
The public Kuiper entry now allocates the final (N,N) result itself and returns
it with the matmul/triangular postcondition.  The C++ boundary only validates
contiguous inputs, calls that entry once, and wraps the returned pointer; it
does not copy inputs, allocate an output, or reshape a flat Torch allocation.
Any contrary bridge description below is historical and superseded.

Skeptic review -- KB L1 challenge 14 (triu(A @ B))
===================================================

Reference: C = torch.triu(torch.matmul(A, B)), A, B (N, N), N = 4096.

Verified component
------------------
EVERYTHING on the GPU is verified.  The single extracted entry
Kuiper_KB_TriuMatmul_triu_matmul_f32(uint32_t n, float* A, float* B, float* Y)
performs one launch in place on Y.

For a retained cell (i,j), i <= j, the kernel accumulates only k=i..j.
Terms k<i vanish because A is upper triangular; terms k>j vanish because B
is upper triangular.  For i>j it writes zero without performing a product.
The proof establishes that upper-triangular matrices are closed under matmul
and that the shortened reduction equals the ordinary dense MS.matmul.

The exported postcondition directly states Y %~ MS.matmul A B.  The closure
theorem proves that this dense result is already upper triangular, so it is
also the KernelBench triu(matmul(A,B)) reference result.

No assume / admit / magic / --admit_smt_queries is used.

Unverified glue in the .cu bridge
---------------------------------
NONE of the math.  The bridge performs dtype/device/shape and ABI-range checks,
makes contiguous inputs, allocates the output, calls the verified entry, and
reshapes the flat allocation to (N,N).  It contains no torch::triu call.

The theorem is conditional on A and B being upper triangular, matching
KernelBench's input generator.  The bridge does not scan arbitrary caller
inputs to revalidate that semantic precondition; doing so would add an O(N^2)
pass outside the kernel.  Calls with non-triangular inputs are outside the
verified entry's contract.

Performance note
----------------
The kernel performs N(N+1)(N+2)/6 scalar products instead of N^3 and has no
separate masking launch.  Its specification explicitly requires the real
witnesses for A and B to be upper triangular; concrete skipped entries need
only approximate those real zeroes.
