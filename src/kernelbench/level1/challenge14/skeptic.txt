Skeptic review -- KB L1 challenge 14 (triu(A @ B))
===================================================

Reference: C = torch.triu(torch.matmul(A, B)), A, B (N, N), N = 4096.

Verified component
------------------
EVERYTHING on the GPU is verified.  The single extracted entry
Kuiper_KB_TriuMatmul_triu_matmul_f32(uint32_t n, float* A, float* B, float* Y)
composes two launches in place on Y:

  1. GEMM: Y := A @ B via Kuiper.Kernel.GEMM.Naive3.mmcomb_gpu_approx.
  2. triu: Y := s_triu Y via the generic verified in-place kernel
     Kuiper.Kernel.Triu (src/lib/kernel/Kuiper.Kernel.Triu.fst).

The exported postcondition states, for every output (i,j), that the result
approximates the real matmul entry when i <= j and is exactly zero when i > j.
The complete KernelBench operation is therefore covered by one Kuiper theorem.

No assume / admit / magic / --admit_smt_queries is used.

Unverified glue in the .cu bridge
---------------------------------
NONE of the math.  The bridge performs dtype/device/shape and ABI-range checks,
makes contiguous inputs, allocates the output, calls the verified entry, and
reshapes the flat allocation to (N,N).  It contains no torch::triu call.

Performance note
----------------
Like challenge 15, this deliberately closes the proof gap by composing a full
dense GEMM with a verified mask.  It does not yet exploit triangular inputs to
avoid computing entries that will be zeroed.
