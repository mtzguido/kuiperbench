Skeptic review — KB L1 challenge 1 (matmul wrapper)
========================================================

Verified component
------------------
The bridge calls [Klas.GEMM.Naive3.g_matmul_f32_rrr]. Its contract
directly relates the output to real matrix multiplication and permits
an output grid up to [max_blocks * max_threads] elements. The earlier
Naive2 rank-2 entry was unsuitable here: its [m*n <= max_blocks]
precondition excludes the benchmark's 4096x4096 output.

KernelBench problem shape
-------------------------
Square matmul C = A * B with N = 4096 (fp32, row-major, CUDA).
The 16,777,216-element output is well below Naive3's verified
2,147,483,648-element launch bound.

Unverified glue in the .cu bridge
---------------------------------
Naive3 is not tiled, so the bridge passes the original row/shared/column
dimensions directly. There is no padding or result slicing. It makes
the inputs contiguous and allocates an exact-shape output.

Bridge defensive checks (added post-review)
-------------------------------------------
TORCH_CHECK validates dim==2, inner-dim agreement, fp32 dtype, CUDA
placement, device match, positive dimensions, overflow-safe layout
products, uint32 ABI bounds, and Naive3's exact output-launch bound
before dispatching. These produce clearer errors than a silent
illegal-memory-access if the bridge is ever reused outside KernelBench.
.contiguous() on both inputs guarantees row-major (cols, 1) strides,
matching the Kuiper kernel's i*N + j flat indexing.

Result
------
No new verified Kuiper code was written for this challenge; this is
a thin bridge over the packaged Klas.GEMM.Naive3 primitive. The prior
KernelBench run covered the old bridge; this environment could not
compile the revised extension because Python development headers are
absent, so the new dispatch still needs a CUDA integration run.
