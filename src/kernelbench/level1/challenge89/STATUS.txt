Why the kernel side is deferred
-------------------------------
The KernelBench input has 32768 elements along the scan axis.  A
single-block Hillis-Steele or Blelloch scan is bounded by [max_threads]
(≤ 1024 in current Kuiper), so it does not cover this input.  A
shippable kernel therefore needs a *two-pass multi-block scan* with
explicit carry-propagation:

    Pass A: per-block inclusive scan, write block sums to an aux array.
    Pass B: scan the aux array (recursive, or one extra block once
            n_blocks <= max_threads).
    Pass C: add the (exclusive-)prefix of the aux scan to each
            block's elements.

Each of the three passes carries its own Pulse / separation-logic
invariant and shared-memory state.  The closest existing primitive is
[Kuiper.Kernel.HReduce.Block.reduce_batched_block] (706 lines), which
maintains a per-block running fold but writes only the *final* fold,
not the per-element prefixes — so its proof skeleton is reusable for
Pass A but does not directly carry through for the scan output.

A careful single-block scan primitive (covering scan dims ≤ 1024
elements, useful for some KernelBench L2 inputs but *not* for the
32768 inputs of #89–#93) is itself an estimated 600–800 line proof.
The multi-block extension adds another 400–600 lines.  This is well
over the 2-hour wall budget for this work item — per the project rules,
ship the spec and stop, with the bring-up plan below.

Why this is not a runnable solution to #89 yet
----------------------------------------------
KernelBench L1 #89 has input shape (32768, 32768), so
  rows * cols = 32768 * 32768 = 2^30,
which exceeds [max_blocks * max_threads ≈ 2^26] in current Kuiper.
The primitive's precondition therefore *cannot* be discharged at
the KernelBench input shape — calling it from a #89 wrapper compiles
but blocks at the precondition pure assertion.

Two paths forward (left for the next session):

A. Multi-block scan primitive.  Three-pass Hillis-Steele /
   Blelloch as outlined above (Pass A/B/C, ~1000-1400 LOC of new
   Pulse).  Once landed, all five challenges drop in.

B. Per-challenge wrappers against [scan1d_inclusive] for *small*
   inputs.  These would verify (the spec→primitive bridge is clean
   via [Kuiper.Approximates.sum_is_approx]) but the runtime
   harness would have to be skipped at the KernelBench shape.

Bridge sketch for path B (#89 wrapper):

   Goal:   scan2d_inclusive_post m_real b d sx sy
   Have:   sy == scan2d_inclusive_result m_fadd_f32 sx
   Each cell:
     macc sy r i == scan_inclusive_at m_fadd_f32 (row r) i
                 == red_fold m_fadd_f32 0.0f32 (slice (row r) 0 (i+1))
                 == seq_fold_left add zero (slice (row r) 0 (i+1))
     by  sum_is_approx
                 %~ seq_fold_left (+.) 0.0R (slice (real_row r) 0 (i+1))
                 == red_fold m_real 0.0R (slice (to_real_seq (row r)) 0 (i+1))
                 == scan_inclusive_at m_real (to_real_seq (row r)) i.
   QED, modulo a slice-of-to_real_seq lemma.

The same shape applies to #90 (need [reducer_fmul_f32] axiom in
[Kuiper.Monoid.Reduce.F32], plus a [prod_is_approx] in
[Kuiper.Approximates] mirroring [sum_is_approx]), #91 (extra
[seq_rev] bookkeeping), #92 (one-cell shift), and #93 (a [mask_seq]
pre-pass via [Kernel.Map2]).
