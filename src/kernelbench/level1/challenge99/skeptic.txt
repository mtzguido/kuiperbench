# Skeptic review — KernelBench L1 #99 (TripletMarginLoss)

Updated: 2026-08-31

## Verdict

The current functional contract is input-dependent and matches the pinned
KernelBench reference parameters: `p=2`, `eps=1e-6`, `swap=False`, and
`reduction='mean'`.

For every row and pair `(x,y)`, the verified distance computation is:

    sqrt(sum_j ((x[j] - y[j]) + eps)^2)

This is PyTorch PairwiseDistance's epsilon placement, not merely an epsilon
outside the square root. For every real sequence approximated by each f32
input, the postcondition directly states that the f32 result approximates the
real triplet loss. Its real distances use `FStar.Math.Sqrt.sqrt`; there are no
existential intermediate distances, square roots, loss terms, or reductions.

The earlier Phase-0 loose-witness discussion was about an obsolete version of
the specification and has been removed rather than retained as misleading
current documentation.

## Implementation correspondence

- `sq_diff_step_f32 eps x y` computes `(x - y + eps)^2`.
- `dist_sq_row` maps that operation over a genuine copied input row and reduces
  it, with a postcondition using `real_sq_dist eps` on the same row.
- The loop computes anchor-positive and anchor-negative distances, takes their
  f32 square roots, and stores `max(0, d_ap - d_an + margin)`.
- The public entry point computes the f32 reciprocal from the batch size and
  multiplies the final reduction by it; callers cannot supply a mismatched
  scale.
- The C++ bridge supplies the pinned PyTorch default `eps=1.0e-6f` to the
  verified entry point.

The extracted ABI is:

    triplet_fw_f32(B, D, margin, eps, anchor, positive, negative)

and the bridge uses that order.

## No fallback

`ModelNew.forward` always calls the Kuiper extension. Unsupported device,
dtype, rank, shape, or size inputs fail the bridge's `TORCH_CHECK` conditions;
they are not silently redirected to PyTorch. This keeps the implementation
boundary explicit and ensures the submitted model has only one semantic path.

## Trust and performance qualifications

The challenge module contains no `assume`, `admit`, or `magic`, but it uses
three compatibility/shared components with explicit repository-level trust
obligations:

- `Kuiper.KB.Compat.SqrtApprox.sqrt_approx` is a temporary local `assume val`
  for the missing floating/real square-root approximation law. The proposed
  upstream change is `patches/kuiper-sqrt-approx.patch`; it uses
  `FStar.Math.Sqrt.sqrt` and has been checked against the pinned package.

- `Kuiper.KB.Compat.Array.gpu_memcpy_device_to_device'` currently has an
  admitted proof of its exact offset-copy postcondition.
- `Kuiper.Kernel.HReduce.reduce` currently uses `magic()` for two sendability
  obligations.

The implementation is also intentionally slow: it performs two per-row map and
reduction sequences before the final batch reduction. This is a performance
issue, not a specification looseness issue.
