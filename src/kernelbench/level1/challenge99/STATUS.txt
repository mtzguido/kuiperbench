STATUS — KernelBench L1 #99 TripletMarginLoss
=============================================

CURRENT STATUS (2026-09-03)
---------------------------
The bridge performs validation and one call to `triplet_fw_f32`; that entry
narrows the Python `f64` margin and supplies the fixed `1e-6f` epsilon. All per-row
orchestration, copies, reductions, square roots, reciprocal
computation, result allocation, and final mean are inside Kuiper.  There is no
host algorithmic loop and no fallback.  The launch-heavy per-row composition
is a verified implementation/performance qualification, not host-side glue.
The older phrase "per-row host orchestration" below is superseded.

Updated: 2026-08-31
Status: verified and extracted; CUDA runtime test requires an available GPU.

Current semantics
-----------------

The implementation matches the pinned PyTorch defaults:

  p=2, eps=1e-6, swap=False, reduction='mean'

For each row it computes:

  d_eps(x,y) = sqrt(sum_j ((x[j] - y[j]) + eps)^2)
  loss = mean(max(0, d_eps(anchor,positive)
                     - d_eps(anchor,negative) + margin))

The `eps` term is present in the Kuiper specification, proof, extracted CUDA,
and bridge ABI. The bridge passes `1.0e-6f`.

The exported entry point derives the mean reciprocal from `B` internally;
`inv_b` is not a caller-controlled ABI argument.

The postcondition quantifies the real input sequences at the entry point and
directly states that the result approximates the corresponding real loss. It
contains no existential distance, square-root, loss-term, or reduction
witnesses. The real distance uses `FStar.Math.Sqrt.sqrt`.

Verification boundary
---------------------

`ModelNew.forward` has no PyTorch fallback. Every call goes to the Kuiper
extension; unsupported inputs fail the bridge checks.
