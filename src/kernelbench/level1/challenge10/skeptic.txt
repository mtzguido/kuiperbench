(b) DOES THE SPEC CAPTURE 3D BATCHED MATMUL?
--------------------------------------------
Yes. Precond `flat3to2 eA %~ rA`, postcond `flat3to2 eC' %~ MS.matmul rA rB`.
Because content_ok proves flat3to2 IS the batched row-major flatten, and
B is the SAME matrix for every (N,M) slice, "flatten then 2D matmul" is
provably identical to per-slice batched matmul. The spec is the standard
Kuiper real-number approximation (%~) of the Kahan-summed Naive3 kernel;
rA is a free real reading tied to the stored fp32 only via %~. Acceptable.
Cancellation risk at atol=rtol=1e-4: NONE of concern. Inputs are U[0,1),
so every product is non-negative and the K=2048 reduction is a sum of
non-negative terms (magnitude ~512) — monotonic accumulation, no
catastrophic cancellation. Kahan summation keeps error O(eps) independent
of K. Comfortably within 1e-4 rel/abs tol. The reference (cuBLAS fp32)
has comparable rounding. Not a risk.

(d) SOUNDNESS GAPS (real, ranked)
---------------------------------
*** Medium — INCOMPLETE uint32 overflow guards in the bridge. ***
  SZ.fits <==> fits in 32 bits (Kuiper.SizeT: SizeTFitsU32). So every
  Array length must be <= 2^32-1 for the `gX |-> ...` preconditions to
  even hold; the untrusted bridge is the TCB boundary that must enforce it.
  Buffers: gA length = N*M*K, gB length = K*L, gC length = N*M*L.
  The bridge enforces N*M <= U32MAX and (N*M)*L <= 2^31-1 (covers gC and
  the n*^m multiply), but does NOT check:
      - N*M*K <= UINT32_MAX   (gA buffer / index trow*k)
      - K*L   <= UINT32_MAX   (gB buffer / index anf0*l)
  Individual dims being <= U32MAX does NOT bound these products. The
  extracted kernel computes indices `gA[trow*k + ...]` and `gB[anf0*l + ...]`
  in uint32 arithmetic; if N*M*K (or K*L) exceeds 2^32 the multiply wraps
  mod 2^32 -> silently wrong (or OOB) reads, i.e. results that diverge from
  the verified spec. The verified module is NOT at fault — its precondition
  is simply under-enforced by the bridge.
  NOT triggered by the benchmark: N=16,M=1024,K=2048,L=768 gives
  N*M*K=3.36e7, K*L=1.57e6, N*M*L=1.26e7 — all far below 2^32. So run.sh
  passes and the default tensors are safe. The gap only bites for very
  large K or L (multi-GB operands). Recommend adding the two missing
  TORCH_CHECKs to fully close the TCB boundary.

  Non-issues (checked and cleared):
  - szp-vs-nat nm=n*m: handled by entry_eq (propositional eq, no transport);
    extracted `nm=n*m` guarded by N*M<=U32MAX.
  - ghost reshape: confirmed zero runtime code in obj/Kuiper_KB_MatmulND.cu.
  - A3/A2 aliasing: linear ownership transfer, no double-ownership.
