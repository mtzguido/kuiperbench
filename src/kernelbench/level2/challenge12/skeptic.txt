(a) Float branch vs torch LeakyReLU boundary — MATCHES (no observable diff)
--------------------------------------------------------------------------
Closures:
  leaky_relu slope v = if gte v zero then v else mul v slope
  mul_lrelu mult slope v = leaky_relu slope (mul v mult)
Spec asserts output == mul_lrelu mult slope (matmul+bias), float-level ==.

Boundary analysis (the thing you flagged):
  - v = +0.0: gte (+0.0) (+0.0) = true  -> returns +0.0.
    torch leaky_relu(+0.0) = +0.0 either way (0*slope = +0.0). MATCH.
  - v = -0.0: IEEE (-0.0) >= (+0.0) is TRUE, so closure returns v = -0.0.
    torch returns -0.0 (or -0.0*slope = -0.0). Same value. MATCH.
  - Whether torch internally uses ">" or ">=" is irrelevant here: at the only
    ambiguous point (±0) both formulas yield a zero of identical magnitude, and
    the eval tolerance (atol=rtol=1e-4) does not distinguish signed zero anyway.
  - NaN: torch.rand inputs => no NaN reaches the op; moot.

Caveat worth stating (NOT a bug): the floating typeclass model
(Kuiper.Floating.Base.fsti, line ~49) explicitly conflates +0.0 and -0.0 under
propositional ==. So the *spec* cannot even talk about signed-zero distinctions;
it is an abstraction over IEEE. The extracted CUDA still performs a real
`v >= 0.0f` compare on the GPU. This is a modeling abstraction, not a soundness
hole, and has no effect on the benchmark outcome.

--------------------------------

    exactly the [wt] layout the kernel expects. CORRECT.
  - bias length: TORCH_CHECK B.size(0) == out, B is 1-D. Spec indexes bias by

  - ABI bounds: guards batch,input,out > 0; each <= UINT32_MAX; each pairwise
    product <= UINT32_MAX (matches SZ.fits requirements); and
    batch*out <= KUIPER_MAX_BLOCKS*KUIPER_MAX_THREADS. Verified that
    KUIPER_MAX_BLOCKS = 2097152 == Kuiper.Base.max_blocks (pow2 21) and
    KUIPER_MAX_THREADS = 1024 == max_threads. Matches the .fsti precondition
    batch*out <= max_blocks*max_threads. CORRECT.
  - dtype/device guards: X/W/B checked float32 + is_cuda + dims (2/2/1); all on
    same device. CORRECT.
  - reshape: Y allocated flat {batch*out}; kernel writes row-major i*out+j;
    reshape({batch,out}) is row-major => element (i,j). CORRECT.
  - double->float casts: (float)mult, (float)slope. mult=2.0 exact; slope=0.1
    becomes 0.1f, which is exactly what torch's float32 LeakyReLU uses when the

  - Contiguity: Xc, Wt, Bc all .contiguous() before data_ptr. CORRECT.

(e) Silent-wrong-answer / order-of-ops — CORRECT
------------------------------------------------
torch order: linear = x@W.T + bias; then * multiplier; then leaky_relu.
Spec: mul_lrelu mult slope (add (macc (matmul sx swt) i j) (bias@!j))
    = leaky_relu slope (mul (matmul+bias) mult).
So bias is added BEFORE the multiply, multiply BEFORE leaky_relu. Exact match.
Implementation realizes this in the same order: GEMM -> bias-add (into y) ->
fused (y*mult then lrelu). No reordering, no bias-after-mult bug, no
lrelu-before-mult bug. Float multiply is commutative so mul v mult == mult*v.
