(a) GENUINELY VERIFIED vs ASSUMED
---------------------------------
VERIFIED (at the float typeclass level, EXACTLY — no real-number approx):
  Output sy'[i*out+j] == sig_scale_res sf (macc(matmul sx swt) i j + bias[j])
  where
    sigmoid v       = div one (add one (exp (sub zero v)))   = 1/(1+exp(-v))
    sig_scale_res    = add (mul (sigmoid v) sf) v            = sigmoid(v)*sf + v
  This is the exact torch op order (sigmoid(g)*sf + g, g = x@W.T+bias).
  The pipeline is three real verified kernel launches:
    1. P.mmcomb_gpu_exact  -> gC = x @ wt (exact, eC' == matmul sx swt)
    2. BA.bias_add_gpu     -> y[i*out+j] = C[i,j] + bias[j]
    3. Map.map_gpu (sig_scale_res sf) -> fused pointwise
  The per-(i,j) postcondition is discharged by gssr_row_aux via
  BA.bias_add_at_ij + lseq_map, then Classical.forall_intro_2. No shortcuts.

  inline_for_extraction noextract CONFIRMED PRESENT on both sigmoid (fsti:39)
  and sig_scale_res (fsti:44). This is the attribute whose ABSENCE originally
  caused the Karamel failure "Cannot re-check sigmoid__float as valid Low*";
  it is now in place, so the noted re-verify+re-extract is consistent with the
  current source. Good.

ASSUMED / EMPIRICAL (NOT covered by the proof — be honest):
  * Kuiper `exp` extracts to CUDA `expf`. The verified spec guarantees the
    output equals the FLOAT expression 1/(1+expf(-g))*sf + g. It does NOT
    prove this equals torch's sigmoid bit-for-bit. torch.sigmoid uses its own
    (typically more numerically stable) kernel, not literally 1/(1+expf(-x)).
    Agreement is EMPIRICAL — the test passes at atol=rtol=1e-4. This is a real
    transcendental-equivalence gap, acceptable under KernelBench tolerance but
    worth stating: "verified == correct float formula", not "verified ==
    bitwise torch".
  * Numerical edge behavior of 1/(1+exp(-v)):
      - v very negative: exp(-v) -> +inf, 1/(1+inf) = 0  (matches torch -> 0)
      - v very positive: exp(-v) -> 0,   1/(1+0)   = 1  (matches torch -> 1)
    No NaN is produced (1/inf is well-defined 0 in IEEE). So overflow/underflow
    does not diverge from torch in the limits. For mid-large |v| the two
    formulas can differ by a few ULP, but stays within 1e-4. Inputs here are
    torch.rand (x in [0,1)) through a random Linear, so |g| is moderate and
    this is a non-issue in practice. Noted only for completeness.
